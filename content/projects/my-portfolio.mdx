A handcrafted portfolio built with **Next.js**, **React**, and a bunch of small but interesting UI challenges.

This project was used as a sandbox to sharpen patterns, rethink mental models, and build small reusable components. The result is a site that feels simple on the surface, but hides quite a bit of thoughtful engineering underneath.

### A flexible three-column layout using CSS Grid

The layout uses a simple 3-column grid that lets most content sit naturally in the central column while certain sections expand outward for greater prominence. Because the side columns scale smoothly around breakpoints, the page feels consistent without having to rely on precise media queries.

<ExpandableSection title='How the grid words'>

Initially for the layout, I had a single central column using a combination of two low-level components (MaxWidthWrapper and Section), that basically added some padding and set the inline margins to `auto` to help centralise the content.

This worked fine initially, where any time I needed to have the content break slightly wider I could use negative margins. But later when I wanted to do fancier things like have sections of the page break even wider in a smooth way, using negative margins wasn't really feasible.

I remembered another site that had something similar to what I was looking for and after inspecting how it was done in the devtools, I switched to this layout pattern instead:

```css
.layout {
  display: grid;
  grid-template-columns:
    1fr
    min(var(--trimmed-content-width), 100%)
    1fr;
  max-width: var(--outer-content-width);
  margin: 0 auto;
  padding-inline: var(--viewport-padding);
}
```

Instead of a single central column, we now have a **3-column grid**.

The way it works is the central column will have a minimum width of either 100% or a defined set width (`--trimmed-content-width`). So on smaller viewports, the width is 100% and the side columns have zero width. But as the viewport grows beyond `trimmed-content-width`, the side columns _equally share_ the available space until that maximum width is hit.

This behaviour opened up different possibilities with where I put sections on the page. By default, the content is funnelled towards the central column, but if I wanted I could assign any child of the grid to use the side columns too. This made things much smoother around key breakpoints, and negated the need for using media queries that could produce jerky effects.

This wouldn't be the first time I found myself being surprised at how useful and powerful CSS Grid can be.

</ExpandableSection>

### A scalable Card component system

A shared base Card component keeps the structure, spacing and behaviour consistent for all cards, but its API is designed to allow aspects of its style to be changed, making it easy to introduce variants.

<ExpandableSection title='The Card design'>

One of the things I like about the component-driven architecture of React is that it lends itself to easily composing components based off other components. In a well-designed React app, I believe there is a **spectrum of components**, where on one side you have your low-level, generic components, and then as you move along the spectrum, the components become more complex or baked-in until you
get to the entire app.

At one point in developing this site, I had 3 different card components, and so this made me think about the spectrum and how I could refine my design. It made sense to extract a low-level, generic `Card`, from which the other three cards could become variants thereof.

A tricky part was figuring out how to configure the correct API so that a variant card could override the base card styles. For example, if I wanted my card to have `8px` of `border-radius` instead of the default `12px`, how should that work?

Initially, I thought the order mattered and so including the more speficic styles _after_ the base styles would solve this. But it didn't, presumably down to how CSS modules are compiled in React, I'm guessing. At any rate, a solution I found was to expose CSS properties in the base card to accept _CSS variables_ as values. Then in the CSS for the variant cards I could define what values these CSS variables would hold. This approach required adjusting my **mental model** for dealing with such abstraction of components when using CSS modules:

## The hiding `Header`

A cool thing I've noticed on other sites is the 'hiding header' - a header that will _hide on scroll down, reappear on scroll up_. I wanted the same behaviour here, and it turned out to the trickier than I expected.

My first attempt was straightforward:

```js
function useScrollDirection({ initialDirection = 'up' }) {
  const [scrollDir, setScrollDir] = React.useState(initialDirection);
  const [scrollY, setScrollY] = React.useState(0);

  const threshold = 10;

  React.useEffect(() => {
    const handleScroll = () => {
      const currentScrollY = window.scrollY;

      if (currentScrollY > scrollY && currentScrollY > threshold) {
        setScrollDir('down');
      } else if (currentScrollY < scrollY) {
        setScrollDir('up');
      }

      setScrollY(currentScrollY);
    };

    window.addEventListener('scroll', handleScroll, {
      passive: true,
    });

    return () => window.removeEventListener('scroll', handleScroll);
  }, [scrollY]);

  return scrollDir;
}
```

This works - but it's not ideal. Because `scrollY` changes constantly, the effect runs constantly too. The event listener is torn down and re-attached every time, and the component re-renders on every single scroll event. Furthermore, scroll events could fire numerous times per second, so this approach doesn't scale well.

### Using refs + `requestAnimationFrame`

The fix firstly involves using a _ref_ to store scroll position instead of using _state_.

```js
const lastScrollY = React.useRef(0);
```

Refs persist across renders without causing re-renders, so this was ideal for storing scroll values rather than using state. Crucially, it meant I didn't need to put any state carrying scroll values in the dependency array of the effect, so it only runs once and the event listener is only attached once.

Secondly, to prevent React state updating too often, we can wrap the updating logic with [`requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) (RAF). Basically using this helps to throttle state events - so say if React wants to fire off 50 state changes in a millisecond (I don't know, it might be possible), then RAF helps to schedule a state change only once every _frame_ change (which I think is once every 16ms). So this helps to prevent our app from getting hammered with state changes and visually we don't notice any difference (we don't get any weird glitchy side-effects either).

Here's the cleaned up version of the hook:

```js
function useScrollDirection({ initialDirection = 'up' }) {
  const [scrollDir, setScrollDir] = React.useState(initialDirection);

  const lastScrollY = React.useRef(0);
  const ticking = React.useRef(false);
  const threshold = 10;

  React.useEffect(() => {
    const update = () => {
      const current = window.scrollY;

      if (Math.abs(current - lastScrollY.current) >= threshold) {
        const newDir = current > lastScrollY.current ? 'down' : 'up';

        setScrollDir((prev) => (prev !== newDir ? newDir : prev));

        lastScrollY.current = Math.max(current, 0);
      }

      ticking.current = false;
    };

    const onScroll = () => {
      if (!ticking.current) {
        requestAnimationFrame(update);
        ticking.current = true;
      }
    };

    window.addEventListener('scroll', onScroll, { passive: true });
    return () => window.removeEventListener('scroll', onScroll);
  }, []);

  return scrollDir;
}
```

Note: the `ticking` ref helps to schedule the RAF updates. We use a ref here so that its value persists during re-renders, which is what we want.

The end result is we get a smooth animation when the header hides or reappears, our app isn't doing unnecessary state-changing work, and the scroll listener never gets re-created.

## The `ExpandableSection` accordion trick

I wanted to build a section of the page that expanded when clicked. My first instinct was to do it the "React way". I had state tracking whether the user wanted the section opened or not and what the necessary height of the section needed to be to show all of it. An effect would fire every time the user opens the section, calculate and update the height state, and this in turn would be used in a CSS class, making it appear visible.

It worked but later I noticed that if I resized the window while it was open, the section wouldn't naturally adjust because I had nothing to cater for this scenario. When the logical answer was to add a resize event listener, which would have required another effect, that's when the alarm bells started to go off and I began investigating other potential approaches.

As it turned out, CSS Grid has a simple way to make this accordion-like effect really simple.

<ExpandableSection>

### Pretty cool, huh?

</ExpandableSection>

The section becomes a one-row grid whose size is dependent on whether it's open. The collapsed state looks like this:

```css
grid-template-rows: 0fr;
```

And the expanded section becomes:

```css
grid-template-rows: 1fr;
```

Add a transition and that's basically the accordion effect achieved.

So instead of having all that height measuring logic involving multiple state and effects, we only need to use React for the toggle and then CSS, and CSS Grid in particular, can handle everything else. Pretty cool, and a useful reminder of how darn helpful CSS can be to help solve challenges like this.

## Building a reusable `Carousel`

One of the trickier parts of this project was building a fully reusable carousel component from scratch. Some aspects were familiar - splitting the scroll-tracking into a custom hook with event listeners, using CSS variables to support different layout variants, and composing components out of smaller building blocks.

There was another aspect to this challenge that, while subtle, is worth mentioning: **stacking contexts**, and how avoiding the temptation to engage in "z-index wars" made the component far easier to reason about.

I always grimace a little when I see an app use huge `z-index` numbers scattered around the UI. It usually means the developer hit an unexpected stacking issue somewhere and reached for the understandable quick fix. It may solve the immediate problem, but it may only hold for a while, and at the least is confusing and seems inelegant.

I'll admit I did the exact same thing earlier in the project when wrestling with a hiding header and a mobile modal menu. It works... until it doesn't.

When building this carousel, the same problem surfaced again, and this time I wanted to avoid all of that. The component has several elements that need to overlap in a very controlled way:

- the scrollable track,
- the fading edge divs/masks,
- the left/right scroll buttons,
- and the cards inside the track.

Instead of juggling z-index numbers and worrying about which elements may clash with other positioned siblings elsewhere, I realised I could simply **create a fresh stacking context** with a single line of code applied to the parent element:

```css
.trackContainer {
  isolation: isolate;
}
```

This forces everything inside the carousel to stack relative only to this container. No unexpected interference from outside layers, no leaking upwards into global stacking contexts.

Once that's in place, and the internal pieces opt into the positioned layout, you can rely entirely on **DOM order** to determine overlap:

```html
<div className="{styles.trackContainer}">
  {/* Base layer */}
  <div className="{styles.track}">{/* cards */}</div>

  {/* Fade layers (higher because they come later in the DOM) */}
  <div className="{styles.fadeLeft}" />
  <div className="{styles.fadeRight}" />

  {/* Buttons (highest because they're last) */}
  <button className="{styles.leftButton}">…</button>
  <button className="{styles.rightButton}">…</button>
</div>
```

It's a small detail in the context of a fairly involved feature, but it ended up being a really useful pattern - especially when thinking about the component-driven architecture of React and potentially different positioned elements in other parts of the app. It kept everything layered and predictable, without a single z-index number in sight.

## Reworking the contact form - from server action to client logic

I built a contact form where I used the [Web3Forms](https://web3forms.com/) service to help relay messages to my email. My first approach was to handle the logic through a **server action**, because we're in Next.js land, so why not? The server action performed validation with Zod, handled the API request, and returned structured state back to the client. This kept the client component lean.

Maybe the most interesting part of that initial design was the _shape_ of the state returned by the server:

```js
stateStructure = {
  status: 'idle', // idle || success || error
  message: '',
  errors: {},
  values: {},
};
```

By carrying both `errors` and `values` in state, we had a way of preserving the user's inputs and tracking attaching the appropriate error validation messages after the server action ran, allowing React to update the UI accordingly.

This approach worked well... until it didn't. Web3Forms eventually began blocking requests made from server actions. Doing some digging, I found a 2024 blog post on their site - ironically titled [_"Create a Contact Form with Next.js Server Actions"_](https://web3forms.com/blog/nextjs-server-actions-contact-form) - that now contains a 2025 update explicitly advising developers **not** to use server actions for this anymore, instead recommending a fully client-side approach.

### Refactoring the form to run entirely on the client

Shifting everything to the client wasn't overly difficult, but once I did, I noticed that I naturally started thinking more "React-ively". With the server no longer involved, I ended up doing things like introducing multiple pieces of separate state, wiring up controlled inputs, and feeling more confident adding granular interactions.

```js
// The new raft of state - verbose, but cleanly separated
const [formData, setFormData] = React.useState(initialFormData);
const [status, setStatus] = React.useState('idle'); // idle || loading || success || error
const [errors, setErrors] = React.useState({});
const [touched, setTouched] = React.useState([]);
const [feedback, setFeedback] = React.useState('');
```

I started tracking which fields had been interacted with (`touched`) so validation feedback felt more tactile. I was extracting individual rules from the Zod schema to help validate fields incrementally as users typed. The result was a much more responsive form - better than the server-driven version - simply because I was operating inside the React mental model.

What's interesting is that I probably _could_ have implemented these interactive behaviours even with server actions in place. But mixing server-driven workflows with client components made it harder to stay in that mindset. I kept second-guessing when a component "should" be a server component, whether a React Suspense boundary belonged somewhere, whether something would be more efficient on the server, etc.

Ultimately, building this form made me realise that thinking too much about RSC-style optimisations early on can pull attention away from the creative side of development. For future work, I'll probably try to stay in that familiar React client mindset first - then layer in optimisations once the interaction, behaviour, and experience feel right.

## Returning to fundamentals

Having had a short break from web development prior to starting this project, for this portfolio site I felt I needed to simplify the stack to:

- React
- CSS Modules
- Next.js

I didn't want to layer on Tailwind, TypeScript, or other plug-and-play libraries, even though I had experience using them. Instead I wanted to get back to basics and return to the core principles of the component-driven React approach, as well as just get back to writing normal CSS. Next.js wasn't really necessary, but I wanted to familiarise myself with its App Router and the React Server Components 'mode' or paradigm.

In this article, I'll try to go over some of the main talking points looking back on how I've built it so far, focusing mainly on design decisions and technical challenges faced.

## The three-column PageLayout

Initially for the layout, I had a single central column using a combination of two low-level components (MaxWidthWrapper and Section), that basically added some padding and set the inline margins to `auto` to centralise the content. This approach had served me well in the past.

This worked fine initially, where any time I needed to have the content break slightly wider I could use negative margins. But later when I wanted to do fancier things like have sections of the page break even wider in a smooth way, using negative margins wasn't really feasible.

After doing some research, I switched to a popular layout pattern:

```css
.layout {
  display: grid;
  grid-template-columns:
    1fr
    min(var(--trimmed-content-width), 100%)
    1fr;
  max-width: var(--outer-content-width);
  margin: 0 auto;
  padding-inline: var(--viewport-padding);
}
```

The way it works is that we set the width of the central column to a _minimum_ of either a defined set width or 100%. So on smaller viewports, this width becomes 100%, and the side columns have zero width. But as the viewport grows beyond the defined internal width, the side columns equally share the available space up until the maximum width is hit.

This behaviour opened up different possibilities. By default, the content was funnelled towards the central column, but if I wanted I could assign any child of the grid to use the side columns too. This made things much smoother around key breakpoints, and negated the need for using media queries that could produce jerky effects.

This wouldn't be the first time I found myself being surprised at how useful and powerful CSS Grid can be for helping with layout issues where maybe Flexbox or flow layout might struggle.

## Abstracting components

One of the things I like about the component-driven architecture of React is that it lends itself to easily composing components based off other components. In a well-designed React app, I believe there is a **spectrum of components**, where on one side you have your low-level, generic components, and then as you move along the spectrum, the components become more complex or baked-in until you
get to the entire app.

At one point in developing this site, I had 3 different card components, and so this made me think about the spectrum and how I could refine my design. It made sense to extract a low-level, generic `Card`, from which the other three cards could become variants thereof.

A tricky part was figuring out how to configure the correct API so that a variant card could override the base card styles. For example, if I wanted my card to have `8px` of `border-radius` instead of the default `12px`, how should that work?

Initially, I thought the order mattered and so including the more speficic styles _after_ the base styles would solve this. But it didn't, presumably down to how CSS modules are compiled in React, I'm guessing. At any rate, a solution I found was to expose CSS properties in the base card to accept _CSS variables_ as values. Then in the CSS for the variant cards I could define what values these CSS variables would hold. This approach required adjusting my **mental model** for dealing with such abstraction of components when using CSS modules:

<Callout>
  The base component defines the API via CSS variables; variants
  provide the values.
</Callout>

## The hiding `Header`

A cool thing I've noticed on other sites is the 'hiding header' - a header that will _hide on scroll down, reappear on scroll up_. I wanted the same behaviour here, and it turned out to the trickier than I expected.

My first attempt was simple: listen for `scroll` events, store the previous `scrollY` in state, and compare the two values:

```js
function useScrollDirection({ initialDirection = 'up' }) {
  const [scrollDir, setScrollDir] = React.useState(initialDirection);
  const [scrollY, setScrollY] = React.useState(0);

  const threshold = 10;

  React.useEffect(() => {
    const handleScroll = () => {
      const currentScrollY = window.scrollY;

      if (currentScrollY > scrollY && currentScrollY > threshold) {
        setScrollDir('down');
      } else if (currentScrollY < scrollY) {
        setScrollDir('up');
      }

      setScrollY(currentScrollY);
    };

    window.addEventListener('scroll', handleScroll, {
      passive: true,
    });

    return () => window.removeEventListener('scroll', handleScroll);
  }, [scrollY]);

  return scrollDir;
}
```

It works - but it's not ideal. Because `scrollY` changes constantly, the effect runs constantly too. The event listener is torn down and re-attached every time, and the component re-renders on every single scroll event. Scroll events can fire numerous times per second, so this approach doesn't scale well.

### Using refs + `requestAnimationFrame`

The fix involves using a _ref_ to store scroll position instead of using _state_.

```js
const lastScrollY = React.useRef(0);
```

Refs persist across renders without causing re-renders, so here this was perfect for storing scroll values rather than using state. Then I could attach the scroll listener **once**, as there was no need to put any scroll values in the effect's dependency array.

As for the other performance-related issue of updating React state too often, the solution for this involves wrapping our updating logic with [`requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame). This ensures we only compute the scroll direction at most once per animation frame (≈16ms), no matter how many raw scroll events fire between frames.

Here's the cleaned up version of the hook:

```js
function useScrollDirection({ initialDirection = 'up' }) {
  const [scrollDir, setScrollDir] = React.useState(initialDirection);

  const lastScrollY = React.useRef(0);
  const ticking = React.useRef(false);
  const threshold = 10;

  React.useEffect(() => {
    const update = () => {
      const current = window.scrollY;

      if (Math.abs(current - lastScrollY.current) >= threshold) {
        const newDir = current > lastScrollY.current ? 'down' : 'up';

        // Only update state when direction actually changes
        setScrollDir((prev) => (prev !== newDir ? newDir : prev));

        lastScrollY.current = Math.max(current, 0);
      }

      ticking.current = false;
    };

    const onScroll = () => {
      if (!ticking.current) {
        requestAnimationFrame(update);
        ticking.current = true;
      }
    };

    window.addEventListener('scroll', onScroll, { passive: true });
    return () => window.removeEventListener('scroll', onScroll);
  }, []);

  return scrollDir;
}
}
```

We use another ref - `ticking` - to help prevent multiple RAF updates. So, when the first scroll event comes in, we _schedule_ an update for the next animation frame. Any subsequent scroll events that come before that next frame are ignored. When RAF runs, we reset `ticking=false`, so that the next frame can schedule again.

The end result: smooth animation, no wasted work, and a stable scroll listener that never gets re-created.

## The `ExpandableSection` accordion trick

I wanted to build a section of the page that expanded when clicked. My first instinct was to do it the "React way": track open/closed state and run an effect to measure the section's height using a ref. It worked but I later ran into issues when resizing the window while the section was opened, and fixing this would have required adding a resize event listener (more logic).

Then I discovered that CSS Grid could do the heavy lifting to help achieve this accordion effect.

<ExpandableSection>

### Pretty cool, huh?

</ExpandableSection>

Instead of measuring anything, the section becomes a one-row grid whose size is dependent on whether it's open. The collapsed state looks like this:

```css
grid-template-rows: 0fr;
```

And the expanded section becomes:

```css
grid-template-rows: 1fr;
```

Add a transition and that's basically the accordion effect achieved.

So the final version uses React for the toggle and CSS Grid for everything else. A useful reminder that investigating whether CSS and in particular the layout system can help for such problems can help produce a simpler solution than leaning too heavily on JavaScript.
